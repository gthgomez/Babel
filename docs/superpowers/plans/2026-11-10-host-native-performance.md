# Interactive runtime, host-native default, and performance implementation plan

> **For agentic workers:** Execute this plan in dependency order using the user's authorized campaign scope and applicable workspace/resource rules. The plan records requirements; it does not itself grant authority beyond the user's request.

**Goal:** When a person opens Babel, selects a project, and submits a task, begin useful model-backed work promptly, continue the conversation naturally, execute under the selected permissions, and report what actually happened. Reduce measured submission-to-inference and rendering overhead with qualified Desktop runtime reuse. Default ordinary Desktop, interactive CLI/TUI, and non-interactive CLI execution to host-native when no profile is selected; preserve explicit Docker choices and unrelated execution protections.

**Architecture:** Prefer a Desktop-owned, long-lived engine subprocess connected over private inherited pipes, using the existing `ChatEngine`, protocol host, session contracts, and qualified turn preparation where they meet parity requirements. This is a design proposal to validate, not proof that the current protocol host is ready to replace every mode. Keep one-shot CLI commands one-shot and retain useful TUI engine reuse. Make lifecycle and execution isolation separate choices: add a distinct `host_native` default, preserve explicit Docker-backed `safe_repo` and restricted `dev_local`, and pass a validated boundary through each surface. Do not enable the legacy daemon or emulate the new default with a global fallback environment variable.

**Tech stack:** TypeScript/Node.js 22 or 24; Electron and JavaScript Desktop shell; existing Babel policy and test infrastructure.

**Spec:** The behavior, compatibility, and evidence requirements in this document.

## Delivery order and success

Establish the baseline and timing evidence in Task 0A and Task 4. Characterize authority in Task 0B, then implement strict profile resolution, provenance, and legacy-session handling in Task 1 before a host-native default or resident worker is activated. Qualify actual host execution and cancellation in Task 2, then integrate the resident runtime in Task 0C and profile-aware Desktop readiness in Task 3. Tasks 5 and 6 provide bounded context and evidence-driven optimizations; Task 7 qualifies the combined installed product. Root isolation, UI progress, and instrumentation can be prepared independently when their inputs are stable; dependent changes remain gated by the contracts they consume.

The primary outcome is an installable, exercised Windows build, not just a functioning worker or fast mock stream. On a disposable project, Babel must inspect a real bug, make a valid edit, run an actual test, preserve the conversation into a follow-up turn, and report verified, unverified, failed, or cancelled outcomes truthfully. Test failures and unavailable live-provider evidence remain visible. Performance improvement alone does not resolve a reported slow path or crash without corresponding incident evidence. Explicit cross-surface handoff is a separate, nonblocking follow-on within this campaign: it must not delay delivering or qualifying the primary runtime-performance build, and its completion or remaining gap must be reported separately.

## Requested behavior and constraints

- The owner requested the host-native default on all ordinary surfaces, including non-interactive CLI calls that omit a profile. Explicitly selected Docker profiles remain Docker-backed.
- `host_native` executes eligible project commands with the current OS user's authority; it is not an OS sandbox. A subprocess may access host files and network available to that user, regardless of its working directory. Describe this truthfully in Desktop, CLI help, and documentation.
- Keep current approval decisions, protected-path rules, provider/credential handling, process cancellation, Plan read-only semantics, and special isolated execution contracts unless the owner separately changes them. Running a host command is not evidence that its descendants are confined to the project.
- Retain the semantics and aliases of existing named profiles. In particular, `safe_repo` must continue to require Docker and fail closed if its image or engine is unavailable unless an operator explicitly invokes the existing host-escalation mechanism; `dev_local` remains the restricted host-inspection profile absent such escalation. Do not silently downgrade explicit Docker or isolated-review requests.
- Preserve explicitly configured profile choices, environment overrides, image references, and existing project/user data. The new default applies when no explicit choice is present. An unknown explicit or configured profile must not resolve silently to the new host default.
- Distinguish product mode (`chat`/`plan`/`deep`), execution profile, effective host/Docker boundary, approval policy, and session/project authority. A label or persisted descriptor alone does not prove the boundary enforced at a tool call. Record choice provenance and effective boundary without storing credential values.
- New sessions with no explicit profile use host-native. Resume a known legacy Docker boundary as Docker until the user deliberately changes it. For legacy records whose actual boundary or provenance cannot be established, never silently broaden authority: retain a proven prior boundary or require an explicit new choice; non-interactive clients receive an actionable failure rather than an implicit host fallback.
- Do not change the selected model, bypass approvals, alter budget/cost policies, disable verification or recovery, or claim a speedup without evidence. Avoid live provider calls and paid work in automated tests.
- A configured live provider may be exercised only under existing authorization and a bounded cost; never read or print credential-store contents, and never silently switch provider or model. If a live request cannot be run, the model-backed product outcome remains unqualified and the reason is reported.
- Characterize the existing startup and event contracts before changing them. Any change to serialized doctor or runtime metadata is additive/versioned or capability-negotiated and is tested with older and newer Desktop/CLI pairings.

## Session interoperability decision

**Follow-on design:** let a user explicitly resume a Desktop conversation from the CLI/TUI and vice versa while retaining the existing separate store roots. Access the selected session through a controlled reference or handoff; do not automatically merge stores, copy all history, share credentials, or require one always-running process. This supports the same conversation across surfaces without making all local archives visible everywhere by default. The user can continue ordinary conversations in their original surface without a handoff. Implement and qualify this as Task 8, independently of Task 7; it is in the campaign but is not a prerequisite for the primary performance deliverable.

Use a stable session identity and versioned compatible records, mapping legacy chat and thread identifiers only after verifying their actual formats. Require an exclusive cross-process writer/owner fence, physical project identity and policy revalidation, and explicit provider credential resolution in the receiving surface. Do not carry an approval into a different authority context merely because the transcript moved. A source that cannot be safely locked or a newer record that cannot be understood must remain read-only or fail with an actionable error. Preserve the source archive and provide no arbitrary project-controlled filesystem path access. This is a product-scope recommendation, not a claim that today’s stores already interoperate.

## Current evidence and approaches

- Review basis: public Babel commit `65a1c6929e10adbef6ef221b2572f0fd93947d54`; the prior source-test checkout is at `0619ec6a3c02392908796cc180cd1465d1c3c10b`. The reviewed files match across these revisions after line-ending normalization. Re-identify installed artifacts, synchronize an isolated candidate, and revalidate affected facts before implementation.
- Desktop normally launches a new `babel run` child per task and can pass `--resume-chat` to restore a saved session, so a fresh process does not by itself mean prior conversation is forgotten. Its optional shared protocol bridge retains a host, but still launches a `host-run` shim per turn. A successful packaged project-task path with cached diagnostics also launches two credential-capability checks and a doctor CLI; an initially uncached diagnostic can add another check and doctor. These are source-level counts, not measured timings; unpackaged and conversation-only paths differ.
- The protocol host retains engines per thread, durable admission, and lifecycle records, but its Deep adapter is explicitly unsupported. Its preparation path differs from interactive chat preparation. Neither shared `ChatEngine` use nor a healthy handshake is evidence of mode, prompt, policy, provider, approval, or recovery parity.
- The legacy Windows daemon listens on a fixed loopback port and its request dispatcher has no visible client authentication. Its pipeline qualification gate rejects the legacy streaming pipeline, not every daemon method. The separate remote bridge has its own authentication and needs a transport-specific review; neither observation qualifies it as the default local runtime.
- A controlled two-project interleaving against the existing graph implementation produced one relative and one absolute path in a single project's graph because its project root is module-global. Profile and command policy also read process-global environment state; cross-session authority contamination is a risk to eliminate before concurrent mixed-profile work, not a reproduced exploit.
- `ChatExecutionProfile` means `chat`/`plan`/`deep`, whereas `ExecutionProfileName` names policy profiles. The protocol host stores `policyProfile` separately; some paths synthesize a `safe_repo` descriptor. Trace actual enforcement and legacy provenance instead of treating that field as proof of historical isolation.
- Unknown profile strings currently resolve to the default at some call sites; a direct isolated probe confirmed the resolver returns `safe_repo` for a misspelled value at the reviewed revision. Packaged Desktop and the installed CLI use different state roots. A synthetic child-output probe confirmed that after more than 24 MiB the Desktop child reports its display limit but does not observe a later terminal event, even though the child exits successfully. The protocol already has sequence and terminal-lookup concepts to assess for reuse; their presence alone does not prove lossless recovery.
- Windows already has review-specific Job Object support, while other paths use `taskkill`; neither establishes general task descendant ownership. Existing explicitly detached background jobs intentionally survive turn cancellation and require separate ownership and visibility.
- `babel-desktop/native/child.mjs` hardcodes `safe_repo`; CLI defaults also appear in `config/executionProfiles.ts`, `commands/workflowCommands.ts`, and policy/interactive call sites.
- `dev_local` sets `dockerSandbox: false`, but `sandbox.ts` separately rejects project-code commands unless explicit host fallback is authorized. Merely selecting that profile does not supply ordinary host test/build behavior.
- Packaged Desktop checks prerequisites for each project run. `installedDoctor.ts` calls `probeInstalledSandboxImage`, which can inspect an image and run two temporary containers plus cleanup. The source app has different readiness behavior.
- `chatEngineStreamingPreparation.ts` awaits repository context, while admission persists a synchronous checkpoint. The Desktop renderer coalesces text updates per animation frame but rebuilds the visible conversation markup. These are measurement targets, not proven causes of a particular incident.
- A bounded, synthetic shared-symbol probe against the current graph implementation produced 40,000 edges from 200 files and 160,000 from 400 files. This confirms quadratic graph growth for that input; it is not a production latency or crash measurement.
- Alternative A: change `safe_repo` to run on host. Reject: existing explicit calls would silently lose their documented isolation.
- Alternative B: broaden `dev_local`. Reject: existing explicit users and aliases would silently acquire more command authority.
- **Recommended C:** add `host_native` as the new implicit default and preserve both existing profiles. It adds one profile but keeps old choices intelligible and testable.
- For the resident runtime, compare a Desktop-owned private-pipe subprocess against an authenticated bridge and a machine-wide service. Prefer the smallest owned lifecycle that meets requirements; keep the legacy daemon out of the hot path until separately qualified. Measure idle CPU and memory as well as warm latency, and choose prewarming or lazy startup from evidence.

## Review focus

1. Invalid, misspelled, legacy, or mixed-version profile values must not silently turn an explicit isolation request into host execution.
2. A host project command can access outside-project resources under OS-user authority; product wording must not describe path validation as an OS boundary.
3. Plan/read-only modes, privileged action approvals, credential scrubbing, dirty-work protection, and independent isolated reviewer contracts remain effective.
4. Cancellation, Windows child-process trees, container cleanup, and run resumption retain correct ownership when modes differ.
5. Repository-map budget exhaustion, provider failures, renderer/child crashes, and interrupted checkpoint writes must report an honest result and preserve recovery evidence.
6. The resident worker must not allow a project, profile, approval, provider credential, or terminal event to leak into another session. Until isolation is proven, serialize work only if background effects cannot outlive the serialized region; otherwise isolate workers by project and policy.
7. Reconnect and crash recovery must distinguish a confirmed completed action from an unknown outcome. Never replay an external side effect merely because its result was lost.
